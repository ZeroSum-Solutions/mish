# Bundled component payload

This private payload closes the desktop's external Cult UI Pro source-kit dependency. The dated internal-team authorization is in `docs/legal/cult-ui-pro-rights.md`.

`cult-ui-pro/manifest.json` records every shipped file's bytes and SHA-256. The 291 registry snapshots match the catalog pins. All 143 converted page/section layouts include their template, styles and text slots. The 168 app/primitive previews contain self-contained, compressed light/dark HTML generated by the reviewed local harness. They retain mock-data notices and sandbox policies; server-backed demos do not gain working backend integrations.

The daemon resolves this read-only payload from its validated resource root, or the repository during development. `CULT_KIT_DIR` remains an explicit override. Packaged previews require no source-kit folders, Node installation, dependency download, helper process or writes inside the application bundle. Both Catalog UI and `od cult` use the existing local-only routes.

Builds verify the manifest before copying the resource tree. Registry items verify their existing catalog pins when served; preview HTML verifies its compressed file hash before decompression. To refresh the payload, materialize the pinned registry JSON, the three converted files per layout and prebuilt preview HTML; update the complete manifest and verify against the catalog before committing. Keep harvest folders, source-control metadata, tokens, fetch logs, dependency trees and harness process state out of this folder.

The 21st.dev source-kit rows are reference-only. Their private source and bundles are excluded. The independently authored alternatives and licensed GenUI ports remain part of the existing packaged catalog. MotionSites reference briefs and private prompt corpora do not carry a redistribution grant; their raw corpora are excluded. Ordinary provider authentication and external agent CLI installations remain per-user setup.

The TypeScript materializer is `tools/pack/scripts/materialize-component-kit.ts`. Set `CULT_KIT_DIR` and `CULT_PREVIEW_HARNESS_DIR`, then run it with the pinned Node runtime and an empty staging-directory argument. Inspect the result and replace the checked-in payload only after the catalog pins and license scope have been verified. Builds consume the checked-in payload; they never fetch private source or need the external harness.
