# Workbench review decisions

Optional design judgments are advisory. In the review findings list, choose **Accept** or **Dismiss** for each finding. The decision history records the action, UTC time and local user or authorized workspace/member identity. Findings start without a decision. A later decision appends to the history; it does not erase earlier decisions.

Use `od review accept <finding> --project <id> --run <id> --json` or `od review dismiss <finding> --project <id> --run <id> --json`. The existing `od workbench review` prefix supports the same actions. Both call `POST /api/workbench/reviews/:runId/findings/:findingId/decision` with only `{"action":"accept"}` or `{"action":"dismiss"}`. Project scope is required, and the route uses the project's write authority. The daemon supplies the actor and time; clients cannot supply audit fields. Responses use the same review-run view as `od workbench review show` and include each finding's optional `decisions` array.

Headerless requests use the local-owner lane and record `actor: {"kind":"local-user"}` after project write authorization, including when the daemon has an active workspace. This actor identifies local access, not a named member. To attribute a decision to a workspace member, pass `--workspace <id> --workspace-member <id>` together (HTTP headers `x-od-workspace-id` and `x-od-workspace-member-id`). The route uses `resolveMemberVerifiedLocalWorkspaceRequestAuthority` with the daemon's workspace verifier. In directory-backed workspace mode, that verifier checks the signed-in account's membership directory; a forged pair returns `403 WORKSPACE_ACCESS_DENIED` without recording a decision. A partial pair returns `400 WORKSPACE_CONTEXT_INCOMPLETE`. Local/dev mode retains the daemon's static workspace authority. The route never infers audit identity from the active workspace.

Decisions are available after a run finishes and only for findings whose frozen check verdict identifies an applicable optional judgment. Required checks, mechanical checks, unknown applicability and older runs without check verdicts refuse the action with a reason. Collect a new review when a legacy finding lacks those records. Optional judgment decisions do not accept a required project criterion or manual gate.

A decision never changes check verdicts, evidence, reviewer completion, frozen versions or the review outcome. Mandatory failures stay failed; missing required evidence stays inconclusive. The UI explains why required checks cannot be dismissed. Reviews and decisions never edit project files or publish them. Required judgment and manual checks retain their separate acceptance gate.

Contracts live in [workbench-review-decisions.ts](../packages/contracts/src/api/workbench-review-decisions.ts). The daemon serializes decisions per run in [finding-decisions.ts](../apps/daemon/src/workbench/review/finding-decisions.ts) and persists them through the existing review-run store. Review storage follows the root [daemon data directory contract](../AGENTS.md#daemon-data-directory-contract).

## Storage recovery

Review-run read and list responses include `reconciliation` with `state` (`reconciling`, `ready`, or `degraded`) and `failedRunIds` for the authorized project. A temporarily unreadable record or project directory, or a run whose recovery cannot be saved, leaves that project degraded while readable records continue recovery. Corrupt records are logged and skipped during inventory and retries; their bytes stay in place. Other projects can start reviews. A failure to enumerate the whole store still blocks starts until storage recovers.

Start failures use the shared API codes `review-store-degraded` for incomplete recovery and `review-store-unavailable` for an unreadable or corrupt idempotency link. Reads preserve the key index and referenced record. Repair the original data before retrying the same key; the daemon never deletes or reassigns a key during lookup.
