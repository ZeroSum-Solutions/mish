# Inactive placement and launch journal

`journal.ts` records trusted executor/supervisor facts in an explicitly injected SQLite connection. It opens no database and invents no root. The connection must come from the daemon's resolved storage boundary in the root [data directory contract](../../../../../AGENTS.md#daemon-data-directory-contract). `migratePlacementJournal(db)` follows the existing named migration-function pattern. It is not registered in `db.ts`; only the coordinated bootstrap registers it (versioned) on the owned database after native ownership, and the runtime constructs one incarnation and binds `readPreviousIncarnationRecovery` to the coordinator. See [RUNTIME.md](RUNTIME.md). `inspectPlacementJournalReadOnly` is the C2a read-only pre-check for ordinary mode.

Each journal binding supplies a fresh incarnation ID after qualified native ownership. Reusing an ID refuses; a new binding supersedes old handles in SQLite. This is fencing of cooperative journal handles, not kernel ownership. Ownership must precede migration and all other daemon mutation before activation. The store cannot stop external writers or prove that the supplied incarnation belongs to a live owner.

Principal, project and other journal identifiers accept the same maximum200 characters as the source/snapshot and prepared-plan contracts. Receipt and terminal-record reservation uses that bound while retaining the2 MiB record limit.

Every returned write is an outermost immediate transaction on disk WAL with FULL or stronger synchronization and foreign keys enabled. Memory databases, non-WAL modes, weaker synchronization and nesting under an uncommitted caller transaction refuse. Records have a 2 MiB UTF-8 budget; operation creation reserves the worst-case later receipts/terminal fields before any movement. Paths are at most 4096 UTF-8 bytes and launch roots at most 256. Launch persistence uses explicit fields. The claim is committed SQLite recovery after daemon process loss. It does not establish power-loss recovery or flush live files/directories.

Operation keys are scoped to principal, project and apply/undo kind. Equal immutable manifests replay the original record, including after restart; changed input under the same key conflicts. IDs, roots, plan/input digests, ordered movements and independent raw-snapshot references remain bound. Queued/running/done/failed/interrupted are states. Movement intent, movement verified, complete and recovery required are explicit stages. Recovery reports additionally expose conflicts with exact partial locations. No state label authorizes filesystem mutation.

The manifest declares all ordered regular-file retirement/publication/restore steps. Each step binds canonical named source/destination, expected device/inode/raw-byte SHA-256/length and a separately retained immutable snapshot reference. Manifest, file, snapshot and receipt shapes are closed; a snapshot reference is not a moved inode and is not stored raw bytes. The future snapshot store must durably retain and verify the exact bytes, cumulative bounds and independence from mutable named objects. Directory/dependency-tree placement is not represented by this regular-file foundation.

Before each syscall, commit `recordMovementIntent`. Only its `created: true` result can accompany the future first invocation; `created: false` is readback, never permission to repeat a syscall. Commit `recordMovementReceipt` only after the qualified driver and executor verify source absence and the exact moved destination identity/bytes. Matching bytes on a foreign inode refuse. All ordered receipts and linked launch drains are required before `completeOperation`. An interrupted/failed operation with any intent remains recovery required. No automatic retry, cleanup, compensation or reopening of prior operations exists here.

Launch intent is separate from movement intent. Commit `recordLaunchIntent` before spawn. Its `created: false` result must never spawn again. `observeLaunch` records identity only after actual spawn/handshake. Identity includes PID, boot identity, native start identity and supervisor handshake identity; the native PID/boot/start tuple is unique independently of handshake; these must be independently qualified, not invented from a sidecar stamp. `recordLaunchExit` records actual exit evidence for that exact identity. `recordLaunchDrain` records actual owned process-tree/helper drainage after exit. The evidence digests refer to retained trusted observations; syntax-valid hashes alone prove nothing. These methods are private daemon integration APIs, never request/client permission assertions.

PID existence, exit status, helper output, a done/failed/interrupted operation label and kernel lock reacquisition cannot replace those facts. Unknown intent without observed identity stays globally blocked. This increment provides no guessed no-spawn resolution; durable supervisor inventory/handshake qualification is a later gate. Lost helper results require actual exit and drain proof, independently of placement readback.

`classifyRecovery(observations)` is an independent read-only SQLite snapshot; nesting inside an uncommitted outer transaction refuses. It first checks every prior-incarnation launch; any unknown spawn/exit/drain yields global blocked and no project classification. Current launches belong to the current coordinator's retained child tickets, not the prior-incarnation predicate. Superseded journal handles refuse.

After global uncertainty clears, revision-bound current observations classify prior operations. Missing/stale/unknown readback remains recovery required. Changed bytes, recreated names or foreign identities conflict. Complete operations verify the final location map after all steps, so a later publication can reuse a retired source name. Incomplete/lost receipts remain unresolved even when the expected object is currently visible. No receipt is synthesized from readback. An operation-linked live-root launch prevents a no-mutation classification even if movement intent was never observed. Partial observations are returned without removing or replacing any object.

`readPreviousIncarnationRecovery(observations)` supplies F3's future trusted callback: it throws on global uncertainty, otherwise returns sorted exact physical roots of unfinished operations that require recovery or conflict handling. Completed records are checked for full committed receipts and prior launch drainage; later drift is informational for undo/new-plan conflict checks, not a perpetual startup block. Reporting verified for completed history still requires exact readback. The future adapter must obtain fresh qualified read-only observations on each call. The storage API and labels do not grant current principal/project/source authority. Authority-bearing compensation and durable reentry decisions remain separate executor work.

Tests use owned temporary SQLite files. One child runs the actual TypeScript source, commits movement and unobserved launch intents, then kills itself with SIGKILL while SQLite remains open. Reopening preserves both intents and refuses completion/global recovery. This is an actual journal process-loss case with synthetic movement/process facts; it is not a live placement, orphan-process inventory, native movement or production recovery proof.

The migration is registered behind native ownership (see [RUNTIME.md](RUNTIME.md)), and the [adoption executor](ADOPTION.md) supplies the snapshot store, executor I/O and journaled undo. Before wider activation: qualify and connect raw-snapshot/file/directory flush ordering, durable spawn inventory and actual identity/exit/drain observations, fresh authority/reconciliation/compensation, all writers and lifecycle fences, bounded retention, native movement, and the licensed hero HTTP/UI/compiled CLI journey. This increment changes none of those callers.
